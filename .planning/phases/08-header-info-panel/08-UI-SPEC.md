# Phase 8 — UI Design Contract

> Visual and interaction contract for the Header Info Panel + Crumb Chips phase.
> Generated by gsd-ui-researcher; verified by gsd-ui-checker.
>
> NOTE: sops-tui is a terminal UI rendered with `charm.land/lipgloss/v2` over
> `charm.land/bubbletea/v2`. Spacing is in terminal cells (columns/rows), not
> pixels. Typography maps to terminal attributes. Colors are explicit hex
> (`lipgloss.AdaptiveColor` is BANNED — issue #1036).
>
> **This phase is additive on top of Phase 7 + 7.1.** Tokens not covered here
> inherit from `01-UI-SPEC.md` (v1.0 baseline) and `07-UI-SPEC.md` (chrome
> baseline). Phase 8 inflates the 38×6 info-panel slot reserved by D-16 and
> flips the `crumbsHeight` stub from 0 to a real chip-row height.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (TUI — not shadcn) |
| Preset | not applicable |
| Component library | `charm.land/bubbles/v2` (unchanged from v1.0) |
| Styling library | `charm.land/lipgloss/v2` v2.0.3 — `JoinHorizontal`, `JoinVertical`, `Background`, `Foreground`, `Bold`, `Width`, `Height` |
| Text manipulation | `github.com/charmbracelet/x/ansi` v0.11.7 — `ansi.Truncate` (tail), `ansi.TruncateLeft` (head) — both already direct deps |
| Identity parsing | `filippo.io/age` v1.3.1 — `age.ParseIdentities` + type-assert to `*age.X25519Identity` + `Recipient().String()` |
| Git integration | `github.com/go-git/go-git/v5` v5.17.0 — `repo.Head()` + `ref.Name().IsBranch()` + `ref.Name().Short()` |
| Icon library | none — ASCII-only per UI-15; allowed non-ASCII codepoint set extended for `…` (U+2026) only |
| Font | terminal monospace — inherit from user's terminal; no override |

> **Critical constraints (carried forward + Phase 8 additions):**
> - Do NOT use `lipgloss.AdaptiveColor` (issue #1036 hang).
> - Do NOT use `lipgloss.NewStyle()` inside `View()` or any helper reachable from `View()` — grep-gated by `TestViewNoNewStyle` (BFS walker) + `TestSubmodelViewsNoNewStyle` (file-scope walker). Phase 8 extends the sub-model walker scope to `infopanel.go` + `crumbs.go`.
> - Do NOT use any border style other than `lipgloss.NormalBorder()` in chrome files. Phase 8's new `infopanel.go` and `crumbs.go` are **borderless** — they sit inside the existing `InfoPanelPlaceholderStyle` envelope (info panel) and inside a borderless padded row container (crumbs). `TestChromeNormalBorderOnly` scope extends to both files; the test passes because they declare zero borders.
> - Do NOT introduce non-ASCII codepoints in chrome files outside the existing allowlist `─ │ ┌ ┐ └ ┘ ↑ ↓ ← →` plus `…` (U+2026). Phase 8 confirms `…` is already in the `TestChromeASCIIOnly` allowlist (chrome_test.go:53).
> - Do NOT call I/O (`os.Stat`, `os.ReadFile`, `git.*`, `parser.ParseFile`) in `View()` or any reachable helper. The `infoPanel ui.InfoPanelData` cache is the single source of truth. Refresh happens at four event seams (D-213).

### Per-tier visibility matrix (full / mid / narrow chrome tiers)

Phase 7.1 D-116 defines three tiers by terminal width. Phase 8 adds a fourth
row to that matrix (the crumbs row), and the info panel is bound to the full
tier only.

| Tier | Width range | Chrome content | Info panel rendered? | Crumb row rendered? | Body envelope |
|------|-------------|----------------|---------------------|--------------------|---------------|
| Narrow | `width < 41` | 1-row `press ? for help` stub via `ChromeNarrowFallbackStyle` | NO (info-panel slot dropped) | YES (independent of chrome tier per D-216) | `(width, height − 1 chrome − 1 crumbs − 1 status)` |
| Mid | `41 ≤ width < 99` | 2-slot `[menu | logo]`, 6 rows | NO (info-panel slot dropped) | YES | `(width, height − 6 chrome − 1 crumbs − 1 status)` |
| Full | `width ≥ 99` | 3-slot `[info-panel | menu | logo]`, 6 rows | YES — `RenderInfoPanel(m.infoPanel)` rendered into the 38×6 slot | YES | `(width, height − 6 chrome − 1 crumbs − 1 status)` |

Why crumbs render at every tier: D-216 makes the breadcrumb pills a
peer-of-chrome, not a child. At narrow tier, the user still needs to know
"what view am I in?" — the chip row delivers that; the chrome stub is just
help-discoverability. At full tier, the info panel says *where the project is*
(.sops.yaml, age key, git, recipients, file count) and the crumb row says
*where the user is* (files / detail / metadata / etc.). These are orthogonal
context surfaces and never compete for the same row.

### Info-panel byte layout (38-col envelope)

```
┌──────────────────── 38 cells ───────────────────┐
│ cfg:│secrets/dev/.sops.yaml                     │
│ age:│age1abc…xyz                                │
│ rcp:│4                                          │
│ git:│main *                                     │
│ fil:│12                                         │
│     │                                           │   ← row 6 blank by design
└─────┴───────────────────────────────────────────┘
  └─5─┘└──────── 32 cells (or `…`-truncated) ─────┘
```

The label column already contains the trailing `:` colon glyph and a single
space — `cfg:` + ` ` rendered at `Width(5)` produces `"cfg: "` exactly.
There is **no separate `InfoPanelSepStyle` rendered as its own cell** — the
separator is the trailing space inside the label width budget. (The
`InfoPanelSepStyle` style var declared in CONTEXT.md is reserved for a
future Phase 10 visual tweak; Plan 1 may declare it as a no-op style for
forward compat. Recommendation: declare but not render.)

### Crumb row byte layout (any width, full tier example)

```
 <files> <prod.yaml[m]> <metadata>
└┘└─────┘└─────────────┘└────────┘
 1   7         13           10        ← cells
```

- 1 cell of `PaddingLeft` (`SpaceXS`)
- chip 0: `<files>` = 7 cells, rendered with `CrumbChipStyle` (inactive)
- 1 cell separator (single space, no special style)
- chip 1: `<prod.yaml[m]>` = 13 cells, rendered with `CrumbChipStyle` (inactive)
- 1 cell separator
- chip N (last): `<metadata>` = 10 cells, rendered with `CrumbChipActiveStyle` (active)
- 1 cell of `PaddingRight` (`SpaceXS`)

Width budget for overflow detection: `width − 2` (the row padding cells).
When `len(joined chips with separators) > width − 2`, fall back to
`<first> <…> <last>` (D-216 — see Visuals — Crumb row overflow).

Exceptions: none new beyond the per-tier matrix above.

## Typography

Inherited from `01-UI-SPEC.md` and `07-UI-SPEC.md`. Phase 8 introduces
**one new typography channel**: `Bold` weight on the active crumb chip as
a redundant-encoding channel (Pitfall 9, color-only-encoding mitigation).

| Role | Attribute | Phase 8 usage |
|------|-----------|--------------|
| Body | normal weight | Info-panel value column (`InfoPanelValueStyle`); inactive crumb chip text (`CrumbChipStyle`) |
| Label | normal weight + muted color | Info-panel label column (`InfoPanelLabelStyle.Width(5).Foreground(ColorMuted)`) |
| Bold + accent | **bold + ColorBg foreground on ColorAccent background** | Active (last) crumb chip (`CrumbChipActiveStyle`) — the bold weight is the **redundant channel** that survives 16-color downsampling per Pitfall 5 + Pitfall 9. k9s uses bg-only swap; sops-tui adds bold deliberately. |
| Muted | normal weight + ColorMuted foreground | Crumb ellipsis chip `<…>` rendered via `CrumbChipEllipsisStyle`; info-panel `-` empty marker (renders via `InfoPanelValueStyle` per D-204 — no special muting) |

### Rules

- Maximum 2 concurrent text attributes on any single piece of text. The active
  chip is `Bold + Background + Foreground` — the third attribute is the bg
  fill which is structural, not weight/decoration. Counted as 2 (Bold + color
  pair).
- No italic. No underline. No faint/dim except where Phase 1 already uses it.
- No per-frame style allocation — every style declared as package-level `var`
  in `internal/ui/styles.go`. Grep-gated.

### Phase 8 new typography attributes (table)

| Attribute | Where used | Rationale |
|-----------|-----------|-----------|
| `Bold(true)` | `CrumbChipActiveStyle` only | Two-channel encoding (bg swap + bold). Survives 16-color downsample (Pitfall 5). Colorblind-safe (Pitfall 9). |
| `Foreground(ColorMuted)` | `InfoPanelLabelStyle` | Quiet structural text — labels are signposts, not signal. |
| `Foreground(ColorFg)` | `InfoPanelValueStyle` | Value cells carry the actual data; high-contrast default text. |

`ColorAccent` appears only in these specific elements. No other chrome
element may use it.

- Collapse/expand indicator `[+]`/`[-]` on tree nodes (`TreeIndicator`)
- Help panel `?` keybinding key labels (`HelpKeyStyle`)
- Git history commit hash column (`HistoryHashStyle`)
- Bulk-re-key selection indicator (`SelectionIndicatorStyle`)
- Confirm-prompt label `[y/n]` (`ConfirmPromptStyle`)
- Clipboard-hot indicator (`ClipboardHotStyle`)
- Fuzzy-search match highlight (`SearchMatchStyle`)

**From Phase 7:**
- Menu mnemonic labels `[r]` / `[/]` / `[Esc]` etc. (`MenuKeyStyle`)
- Logo foreground at `LogoStatus == LogoInfo` (`LogoStyleInfo`)

**Added in Phase 8:**
- **Active (last) crumb chip background** — `CrumbChipActiveStyle.Background(ColorAccent)` (D-206). The single new accent surface.

**NOT used for in Phase 8:**
- Info-panel labels (use `ColorMuted` via `InfoPanelLabelStyle`)
- Info-panel values (use `ColorFg` via `InfoPanelValueStyle`)
- Info-panel `-` empty marker (use `ColorFg` via `InfoPanelValueStyle` per D-204; no special accent on missing data)
- Inactive crumb chips (use `ColorSurface` bg + `ColorFg` fg via `CrumbChipStyle`)
- Crumb ellipsis chip (use `ColorMuted` fg via `CrumbChipEllipsisStyle`; no bg swap)

- Crumb row PaddingLeft/Right cells (no fill — terminal bg shows through)

### Phase 8 new style declarations (additive to `internal/ui/styles.go`)

All declared as package-level `var`. All testable via `TestViewNoNewStyle`
BFS walker (chrome.go reachable) and `TestSubmodelViewsNoNewStyle`
file-scope walker (infopanel.go + crumbs.go reachable). Eight style vars
total (the seven called out in CONTEXT.md plus a recommended `CrumbRowStyle`
for the row container — see Visuals).

| Go var name | Definition | Purpose |
|-------------|------------|---------|
| `InfoPanelLabelStyle` | `lipgloss.NewStyle().Foreground(ColorMuted).Width(5)` | Label column for `cfg:` / `age:` / `rcp:` / `git:` / `fil:` (D-201). The `Width(5)` enforces 4-char-label + 1-trailing-space alignment without manual padding. |
| `InfoPanelValueStyle` | `lipgloss.NewStyle().Foreground(ColorFg)` | Value column. Width is NOT applied at the style level — value strings are pre-truncated via `middleTruncate` at the helper level (D-203). Plain foreground rendering. |
| `InfoPanelSepStyle` | `lipgloss.NewStyle()` | Reserved for forward compat. Phase 8 does not render an explicit separator cell — the trailing space inside the label `Width(5)` already provides the gap. | `CrumbChipStyle` | `lipgloss.NewStyle().Background(ColorSurface).Foreground(ColorFg)` | Inactive crumb chip pill (D-206). Two-channel encoding: surface bg + fg color contrast. |
| `CrumbChipActiveStyle` | `lipgloss.NewStyle().Background(ColorAccent).Foreground(ColorBg).Bold(true)` | Active (last) crumb chip pill (D-206). **Three-channel encoding: accent bg + inverted fg (bg color used as fg) + bold weight**. Bold is the colorblind-safe redundancy channel (Pitfall 9). |

| `CrumbRowStyle` | `lipgloss.NewStyle().PaddingLeft(SpaceXS).PaddingRight(SpaceXS)` | (Recommended additional var, not in CONTEXT D-208's "7 vars" count but follows from the row-pad requirement.) Row container for the joined chips. Mirrors k9s `crumbs.go:32` `SetBorderPadding(0,0,1,1)`. Plan 1 may inline `PaddingLeft(1).PaddingRight(1)` if preferred — both satisfy the discipline since the var is at package scope. |

### 60/30/10 interpretation for Phase 8

- **60% (Background, `#1e1e2e`):** Terminal background continues to dominate.
  Phase 8 adds the crumb row's PaddingLeft/PaddingRight cells (each 1 col on
  every row's edges) and inter-chip separator cells — all show terminal bg
  through. Info-panel label and value cells render text on terminal bg (no
  fill). Background's share of pixel-equivalent terminal cells stays well
  above 60%.
- **30% (Surface, `#313244`):** Status bar and help overlay continue to be
  the only surface-backed regions in v1.0. Phase 8 adds the **inactive
  crumb chip pills** as new surface-backed surfaces — these are small (≤ 30
  cells per chip × ≤ 8 chips × 1 row) so they remain well below the 30%
  budget. Info panel itself is **bg-transparent** (no surface fill behind
  the 38×6 slot — the `InfoPanelPlaceholderStyle` declares only Width and
  Height, not Background; verify by reading `internal/ui/styles.go:257-263`).
- **10% (Accent, `#89b4fa`):** The active crumb chip background is the new
  Phase 8 accent hotspot. One chip per render, occupying ≤ 30 cells × 1 row
  out of ~12,000 cells at 200×60. Combined chrome+menu+logo+crumbs accent
  usage stays well under the 10% threshold. The active-chip bg + bold pair
  is **the only** new accent fill in Phase 8.

## Copywriting Contract

Phase 8 introduces three new copy surfaces:

1. **Info-panel labels** — five fixed strings, locked verbatim by D-201.
2. **Info-panel values** — derived data (path, fingerprint, count, branch,
   count) with locked truncation/empty-marker rules.
3. **Crumb chip text** — derived from existing `m.status.SetBreadcrumb(...)`
   call-sites, normalised by `<segment>` formatting + lowercase + strip-spaces
   per D-205, D-207.

Phase 8 **does not** introduce new flash messages, new error strings, or new
destructive-confirmation prompts. All such surfaces remain owned by v1.0
sub-models.

### Info-panel labels (locked verbatim — D-201)

The following five strings are the **only** valid labels. Any deviation
(`config:`, `recipients:`, `branch:`, alternate ordering) is a contract
violation.

| Label literal | Render width | Color | Source |
|---------------|--------------|-------|--------|
| `cfg:` | 4 chars + 1 trailing space = 5 cells | ColorMuted | D-201 |
| `age:` | 4 chars + 1 trailing space = 5 cells | ColorMuted | D-201 |
| `rcp:` | 4 chars + 1 trailing space = 5 cells | ColorMuted | D-201 |
| `git:` | 4 chars + 1 trailing space = 5 cells | ColorMuted | D-201 |
| `fil:` | 4 chars + 1 trailing space = 5 cells | ColorMuted | D-201 |

Row order: `cfg → age → rcp → git → fil`. Locked. Any executor reordering is
a contract violation.

### Info-panel values (locked semantics — D-201..D-204, D-214, D-215)

| Row | Value source | Render format | Empty marker condition | Truncation rule |
|-----|-------------|---------------|----------------------|-----------------|
| `cfg:` | `m.infoPanel.SopsYamlRelPath` | repo-relative path string (e.g. `secrets/.sops.yaml`) | `m.sopsYamlPath == ""` → render `-` (D-204) | If `lipgloss.Width(value) > 32` → middle-truncate via `middleTruncate(value, 32)` (D-203) — preserves repo-root prefix + filename suffix |
| `age:` | `m.infoPanel.AgeFingerprint` (full `age1...xyz` string) | always middle-truncated to ≤ 10 cells | parse-failure / file-missing / no-identities → render `-` (D-204) | **Always** middle-truncate to **10 cells** (D-203 `≤10 chars with visible ellipsis`); preserves `age1` prefix + last 2-3 chars of suffix. Example: `age1ab…xyz` = 10 cells |
| `rcp:` | `len(m.currentParsed.Metadata.AgeRecipients)` | integer rendered as decimal | `state == stateFileList` (no current file) OR parse failure → render `-` (D-202, D-204) | None — integers ≤ 4 digits never overflow 32 cells |
| `git:` | `m.infoPanel.GitBranch` + dirty marker | `branch` + ` *` if `GitDirty` (e.g. `main *`); plain `branch` if clean (e.g. `main`); `HEAD@<hash7>` if `GitDetached` | not a git repo / Head() error → render `-` (D-204) | If `lipgloss.Width(value) > 32` → middle-truncate. Branch names rarely exceed 32 cells; defensive only. |
| `fil:` | `m.infoPanel.FileCount` | integer rendered as decimal | pre-FilesDiscoveredMsg (count == -1) → render `-` (D-204) | None |

**Dirty marker glyph (D-215 + Claude's Discretion recommendation):**
- Dirty (any file in `m.files[*].GitStatus != ""`): trailing `" *"` (space + asterisk).
- Clean: no marker. Branch name only.
- Detached HEAD: `HEAD@<7-char-hash>` literal — the `@` distinguishes from a
  real branch named `HEAD`. No dirty marker on detached HEAD (mid-rebase
  states are too transient to surface here).

**Empty marker glyph (D-204):** Single ASCII hyphen-minus `-`, rendered via
`InfoPanelValueStyle` (no muting beyond the value-column foreground). ASCII;
no allowlist change.

**Middle-truncation glyph (D-203):** U+2026 `…`. Already in
`TestChromeASCIIOnly` allowlist (chrome_test.go:53 `'…': true` — verified
2026-04-28). No allowlist change required for Phase 8 either.

### Crumb chip text (locked normalisation — D-205, D-207, D-208)

| Element | Format | Source |
|---------|--------|--------|
| Chip wrapper | `<segment>` — angle brackets, no inner padding | D-205 (k9s `crumbs.go:62-74` verbatim) |
| Inter-chip separator | single ASCII space | D-208 (k9s parity) |
| Row padding | 1 cell left + 1 cell right | D-208 (k9s `SetBorderPadding(0,0,1,1)`) |
| Segment normalisation | `strings.ReplaceAll(strings.ToLower(seg), " ", "")` | D-207 (k9s `crumbs.go:70-71` verbatim) |
| Active chip (last) | `<seg>` rendered via `CrumbChipActiveStyle` (bold + accent bg + bg-color fg) | D-206 |
| Inactive chip | `<seg>` rendered via `CrumbChipStyle` (surface bg + fg) | D-206 |
| Overflow ellipsis chip | `<…>` rendered via `CrumbChipEllipsisStyle` (muted fg, no bg) | D-216 |

**Carry-through note (D-207):** Existing `currentFileBreadcrumb()` in
`internal/app/model.go:1414` appends a git-status badge suffix `[M]` / `[A]` /
`[?]` to filenames. Phase 8's lowercase + strip-spaces normalisation collapses
e.g. `prod.yaml [M]` to `prod.yaml[m]` inside the chip. This is **expected
and accepted** per CONTEXT.md D-207. The redundancy with the new `git:`
info-panel row is mild; the per-file badge anchors per-file state. Stripping
the badge from breadcrumb segments is deferred (out-of-scope cleanup).

### Crumb row overflow rule (D-216 + Pitfall 14)

When `total chip width + (N−1) separators + 2 row pad > terminal width`:

1. Drop the middle-most segment first (the segment whose removal best
   shortens the row while preserving the first-segment "you are in <files>"
   anchor and the last-segment "current view" active highlight).
2. Insert an ellipsis chip `<…>` at the drop site, rendered with
   `CrumbChipEllipsisStyle` (muted fg, no bg).
3. Re-measure. If still overflowing, drop the next middle-most segment.
   Repeat until fits or only `<first> <…> <last>` remains.
4. If `<first> <…> <last>` still overflows: this is a degenerate case at
   widths < ~20 cells. The renderer may either truncate `<last>` itself via
   `middleTruncate` or accept clipping by the row container. Plan 1 author
   picks; recommendation: clip (terminals < 20 cols are unsupported per
   UI-16 anyway).

Plan 1's `truncateSegmentsToWidth` helper implements this iteratively (D-216
explicit budget: ~30 lines). Algorithmic discretion (binary search vs
linear-scan-and-drop) is left to Plan 1 author per CONTEXT.md.

### Status-bar shrink copy (D-209, D-211)

The status bar pre-shrink had three sections: breadcrumb (left), item count
(center), env+clipboard (right), separated by ` | ` pipes. Post-Phase-8 the
status bar contains only the right cluster — env indicators + optional
`[clip]` prefix — right-aligned on the surface bg. **No new copy strings**
are introduced; existing env indicators (`sops:✓` / `age:⚠` / `.sops.yaml:✓`
/ `no git`) are unchanged.

The center-section item count (`12 items`, `47 keys`, etc.) is **deleted**
as a copy surface — the canonical count display is now the titled-border
title from Phase 7 D-15 (`Files (12)`, `History (47)`, `Health (3 findings)`,
`Recipients (4)`).

## Accessibility

Phase 8 accessibility posture (full Phase 10 redundant-encoding scope still
landing in Phase 10 per UI-14):

- **Color-only encoding avoided where possible:**
  - **Active vs inactive crumb chip:** three-channel encoding — bg color
    swap + fg color swap + **bold weight** (D-206). Bold survives the 16-color
    downsample where both `ColorAccent` and `ColorSurface` collapse to similar
    ANSI indices (Pitfall 5). The `<` `>` brackets are also high-contrast text
    that survives any color profile.
  - **Info-panel labels vs values:** muted vs default-fg color provides one
    channel; the structural label position (`Width(5)` left column) provides a
    second channel. Color-only failure mode (16-color `TERM=xterm` collapses
    muted to fg) is acceptable because the layout structure still distinguishes
    the columns.
  - **Empty marker `-` vs valid value:** the `-` glyph is a text channel
    (single ASCII hyphen-minus); no color encoding required. Survives every
    profile.
- **No focus ring:** Phase 8 chrome has zero focus indicators (inherited
  from Phase 7 — Pitfall 7 / D-21 grep-gate enforces no `FocusedBorder` /
  `UnfocusedBorder`).
- **Narrow-terminal survival (40×12):** Phase 8 verifies non-corruption at
  40×12 (narrow tier) — the chrome falls back to a 1-row stub, the crumb
  row may middle-ellipsis to `<…>`-only, and the body region remains
  reachable. Aesthetic polish is deferred to Phase 10 (UI-16).
- **Terminal-emulator portability:** ASCII-only chrome (Phase 8 inherits
  Phase 7's UI-15 contract). The single non-ASCII codepoint is `…` (U+2026);
  font support is universal (every monospace terminal font ships it).
- **Color-profile downsampling:**
  - At ASCII profile (16 colors), `ColorAccent` collapses; the active-chip
    bg+bold encoding preserves the active-vs-inactive distinction via bold.
    Phase 10 (UI-13) adds explicit 16-color fallback palette for clean
    rendering; Phase 8 ships the redundant-encoding mitigation only.
  - At ANSI256 and TrueColor, all colors render as declared.
- **PII / screenshot risk (Pitfall 11):** info panel is the new chrome
  surface that surfaces user-identifying data. Mitigations applied:
  - Age fingerprint truncated to ≤ 10 cells with visible `…` (D-203, D-220).
  - Path strings always repo-relative via `filepath.Rel(cwd,
    sopsYamlPath)` (D-220 question 2).
  - No copy bindings target chrome content (D-220 question 3, also
    architectural — chrome has no input handlers).
  - `$SOPS_AGE_KEY_FILE` env-var path never rendered (D-214; only the
    fingerprint derived from the file at that path is rendered).
- **Keyboard-only access:** unchanged — sops-tui is keyboard-only by core
  value. No mouse interactions on chrome or chips.
- **Screen reader compatibility:** not evaluated (terminal app; out of
  typical a11y scope).
