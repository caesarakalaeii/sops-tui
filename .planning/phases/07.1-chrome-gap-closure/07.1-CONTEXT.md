### Narrow-Terminal Chrome Clamp (WR-03)

- **D-116: Two-tier width fallback in `RenderChrome`.** `internal/ui/chrome.go` `RenderChrome(hints, status, width)` adds two threshold checks before the existing `JoinHorizontal(infoPanel, menu, logo)`:
  - If `width < logoWidth + 8` (~33 cols): render a single-line `press ? for help` stub via a new `ChromeNarrowFallbackStyle` package var (foreground = `ColorMuted`, no border). Returns immediately.
  - If `width < infoPanelWidth + logoWidth + minMenuCol` (~71 cols): drop the info-panel slot. Compute `menuWidth = width - logoWidth`; render menu+logo only via `JoinHorizontal(Top, RenderMenu(hints, menuWidth), RenderLogo(status, logoWidth))`. Returns.
  - Otherwise: existing 3-slot `JoinHorizontal(infoPanel, menu, logo)` path.
  - Constant values: `infoPanelWidth = 38` (matches `InfoPanelPlaceholderStyle.Width(38)` in `styles.go:252-254`), `logoWidth = 25`, `minMenuCol = 8`. Centralise as `internal/ui/chrome.go` package consts so `chromeHeight` and other call-sites can reference the same numbers.
- **D-117: `RenderMenu` manual columns.** Replace the `lipgloss/v2/table` builder in `internal/ui/menu.go:RenderMenu` with manual two-column composition. Each cell becomes `MenuKeyStyle.Render("[" + h.Mnemonic + "]") + " " + MenuDescStyle.MaxWidth(colW - keyW - 3).Render(h.Description)` (the `-3` accounts for `[`, `]`, and the separator space). Then `lipgloss.JoinHorizontal(Top, leftCol, rightCol)` joins the two pre-rendered fixed-width columns. Preserves the 2×6 grid layout from D-04 / D-07 in Phase 7. Side benefit per WR-03: removes the ~394 µs lipgloss/v2/table contribution to the chrome bench, making D-101's 50 µs target more achievable when Phase 11 adds caching.
- **D-118: Visible-hint truncation order.** With manual columns, only the first 12 *visible* (`Visible: true`) hints render. If a sub-model returns more than 12 visible hints, truncate from the tail with no warning (Phase 7's behaviour was the same — `lipgloss/v2/table` silently dropped overflow rows). Keep this behaviour; UI-SPEC ownership of "max 12" stays unchanged.
- **D-119: Goldens refresh.** Regenerate `resize_40x12.golden` (should now show single-line `press ? for help` stub at the top, then the body content underneath up to 12 rows) and `resize_80x24.golden` (should show 6-row chrome with menu+logo only — info-panel dropped). ## Specific Ideas

- **Sequencing risk.** D-101..D-103 (governance restoration) MUST land in the same commit/wave as D-104 (DISCUSSION-LOG entry). A revert without an audit trail is itself a governance failure. Plan should bundle them in a single executor task.
- **Goldens-refresh ordering.** D-114 (120×40, 200×60 goldens after border strip) and D-119 (40×12, 80×24 goldens after narrow-terminal fix) regenerate different goldens. Order matters: do D-112+D-113 (border strip) first, refresh 120×40+200×60, THEN do D-116+D-117 (narrow-terminal fix), refresh 40×12+80×24. Otherwise the second refresh drowns the first in the diff and review becomes harder.
- **Sub-model width-math regression risk.** D-113 changes inner content width arithmetic across 6 sub-models. Use the existing `internal/app/layout_test.go` `TestBodyDims*` patterns as the safety net. If `bodyDims` is the chosen extension point, add tests there first, then implement.
- **AST walker false positives.** The BFS in D-107 may pick up `lipgloss.NewStyle()` calls in test helpers reachable from `View()` only via test-file calls. Constrain the walker to NON-test files only (`!strings.HasSuffix(filename, "_test.go")`).
- **Manual columns in `RenderMenu` (D-117) interaction with `MenuCellStyle`.** Phase 7's `MenuCellStyle` was designed as a `lipgloss/v2/table.StyleFunc` return type. After D-117, it becomes per-cell `MenuKeyStyle` + `MenuDescStyle` directly. Decide: delete `MenuCellStyle` (no longer used) OR repurpose it as a wrapper-style for the entire menu region. Probably delete — package vars should match what's actually rendered.
- **`InfoPanelPlaceholderStyle` survival.** D-116 conditionally drops the info panel at narrow widths. The `InfoPanelPlaceholderStyle` package var stays in `styles.go` — Phase 8 still needs it as the slot the info-panel content will land in. Just don't *render* it at narrow widths.
