## Decisions Made

- **Sequenced D-112 BEFORE D-110:** The plan's "Sequencing critical" note (07.1-PATTERNS.md line 314, 775) is correct — the inner-border NewStyle calls are deletions, not lifts. Doing D-110 first would have introduced a dead-on-arrival `OverlayBorderBoxStyle` package var that D-112 immediately deletes. Net effect: 6 NewStyle calls vanished entirely from the codebase rather than getting lifted to a never-used var.
- **Combined Tasks 1, 2, and 3 into a single atomic commit:** Per the plan's "Step 3.5 — Commit ordering" guidance ("Bundle Tasks 1 + 2 + 3 in a single commit"), the functional change (strip + lift) + the goldens-confirm-unchanged outcome (Task 3) land together. Single commit `2e9a15b`.
- **Goldens were NOT regenerated** (D-114 nuance): The plan's Step 3.1 explicitly anticipated this case — TestResize captures the empty-state initial AppModel which renders `stateFileList`. FileListModel never carried an inner RoundedBorder, so the strip is invisible to TestResize. Verified by running `go test ./internal/app -run "TestResize_..."` post-strip without `GOLDEN_UPDATE=1`: all 4 goldens pass byte-identical. Plan accepts this as the no-diff outcome.
- **D-113 inputWidth math (recipientform.go) kept as `m.width - 12`:** Documented inline derivation. Pre-strip: -12 = -(2 + 10) for inner-RoundedBorder envelope + label budget. Post-strip: -12 = -(4 + 8) for WrapTitled NormalBorder+padding (4 cols total) + an 8-col label budget. Numerically identical, semantically different. Visual verification deferred to manual UAT (see Recommended Future Verification below).
- **OverlayMutedFooterStyle used for recipientform's prompt label** (semantic mismatch — it's a label, not a footer): The byte-identical style chain (`Foreground(ColorMuted)`) and the plan's explicit allowance ("Acceptable to reuse OverlayMutedFooterStyle because the visual chain is identical") justify the reuse. If Phase 8 needs to diverge prompt vs. footer styling, a `RecipientFormPromptStyle` alias can be split out in 1 line.
