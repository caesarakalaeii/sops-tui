# Phase 7 — UI Design Contract

> Visual and interaction contract for the Chrome Skeleton phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> NOTE: sops-tui is a terminal UI rendered with `charm.land/lipgloss/v2` over `charm.land/bubbletea/v2` — not HTML/CSS. Spacing is in terminal cells (columns/rows), not pixels. Typography maps to terminal attributes (bold, dim, normal). Colors are explicit hex values passed to lipgloss (no `AdaptiveColor` — issue #1036 confirmed hang, locked out at project level).
>
> **Phase 7 is additive chrome on top of the stable v1.0 / Phase 6 design system.** This spec extends `01-UI-SPEC.md` (the v1.0 baseline), it does not replace it. Tokens not covered here inherit from Phase 1.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (TUI — not shadcn) |
| Preset | not applicable |
| Component library | `charm.land/bubbles/v2` (list, viewport, spinner, textinput, help) |
| Styling library | `charm.land/lipgloss/v2` v2.0.3 — `NormalBorder()`, `JoinHorizontal`, `JoinVertical`, `Width`/`Height` |
| Grid library | `charm.land/lipgloss/v2/table` — menu grid (`StyleFunc(row, col int) lipgloss.Style`) |
| Form library | `charm.land/huh/v2` (unchanged from Phase 5) |
| Text manipulation | `github.com/charmbracelet/x/ansi` — `ansi.Strip`, `ansi.Truncate` (already direct dep, Phase 6) |
| Icon library | none — ASCII-only per UI-15 (box-drawing from `lipgloss.NormalBorder()` only: `─ │ ╭ ╮ ╰ ╯`) |
| Font | terminal monospace — inherit from user's terminal; no override |

> **Critical constraints:**
> - Do NOT use `lipgloss.AdaptiveColor` — known hang (issue #1036).
> - Do NOT use `lipgloss.NewStyle()` inside `View()` or any helper called from `View()` — grep-gated by `TestViewNoNewStyle` (D-22). All styles declared as package vars in `internal/ui/styles.go`.
> - Do NOT use any border style other than `lipgloss.NormalBorder()` in chrome files — grep-gated by `TestChromeNormalBorderOnly` (D-21).
> - Do NOT introduce any non-ASCII codepoint in `internal/ui/{chrome,logo,menu,crumbs}.go` outside the box-drawing allowlist `─ │ ╭ ╮ ╰ ╯` — grep-gated by `TestChromeASCIIOnly` (D-20). Status-bar flash emoji remain permitted (different file).
> - Do NOT use `RoundedBorder`, `ThickBorder`, `DoubleBorder`, `HiddenBorder`, `FocusedBorder`, `UnfocusedBorder` anywhere in chrome — grep-gated (D-21). ARCHITECTURE.md Pattern 3 pseudocode says `RoundedBorder`; Phase 7 deliberately departs to `NormalBorder` per UI-15.

## Spacing Scale

Inherited from `01-UI-SPEC.md` (Phase 1). Reused verbatim — Phase 7 adds no new tokens.

Terminal spacing is in cells (columns for horizontal, rows for vertical). All values are multiples of 1 cell.

| Token | Go constant | Value | Usage |
|-------|-------------|-------|-------|
| xs | `SpaceXS` | 1 cell | Icon gap, inline separator padding |
| sm | `SpaceSM` | 2 cells | Compact horizontal padding (menu cell gutter) |
| md | `SpaceMD` | 4 cells | Default element horizontal padding |
| lg | `SpaceLG` | 6 cells | Section separation, border + content gap |
| xl | `SpaceXL` | 8 cells | Major layout margin |

Vertical spacing (unchanged from Phase 1):

| Token | Value | Usage |
|-------|-------|-------|
| row-xs | 0 rows | Adjacent items in menu grid / list |
| row-sm | 1 row | Between list sections / group separators |
| row-md | 2 rows | Between major UI regions (reserved) |

Phase 7 fixed dimensions (verified by tests, not tokens):

| Region | Height (rows) | Width (cols) | Source decision |
|--------|---------------|--------------|-----------------|
| Logo | exactly 6 | ~25-26 (26 budget per UI-02) | D-01 |
| Menu | exactly 6 | dynamic (terminal width minus logo, info-panel placeholder, spacers) | D-04 |
| Chrome (logo ⊕ menu ⊕ info-panel placeholder) | exactly 6 (max of children) | full terminal width | D-16 |
| Info-panel placeholder (Phase 8 forward-compat) | exactly 6 | 38 cols recommended | D-16 |
| Crumbs row | 0 (stubbed in Phase 7) | — | D-16 |
| Titled border edges | 1 row top + 1 row bottom, 1 col left + 1 col right | — | D-13 (NormalBorder) |
| Titled content body | `bodyDims(m).h - 2` | `bodyDims(m).w - 2` | D-17 |
| Status bar | exactly 1 (inherited from v1.0) | full terminal width | Phase 1 |

Phase 7 spacing rules:

- Menu cell gutter: render each cell as `[mnemonic] description` with one space between `]` and description (SpaceXS).
- Chrome horizontal composition: `JoinHorizontal(lipgloss.Top, infoPanelBlank, menu, spacer, logo)` — the spacer absorbs remaining width so the logo is truly right-anchored.
- Titled border padding inside border: `Padding(0, 1)` on `TitledBorderStyle` — 0 rows vertical, 1 col horizontal (SpaceXS) per Pattern 3.
- Narrow-terminal exception (40×12): menu may clip to single cell width; acceptable per D-04 "fixed layout at all widths." Responsive stacking deferred to first bug report.

Exceptions: none new.

## Typography

Inherited from `01-UI-SPEC.md`. Phase 7 adds no new type roles — every chrome element reuses an existing role.

Terminal "typography" = text rendering attributes; no font size control.

| Role | Attribute | Phase 7 usage |
|------|-----------|---------------|
| Body | normal weight, no decoration | Menu description column, titled body content |
| Label | bold | (unused in Phase 7 chrome; reserved) |
| Dim | faint/dim | (inherits Phase 1 uses — counts, masked values) |
| Emphasis | bold + accent color | (reserved; Phase 7 uses accent alone for menu mnemonics per D-05) |
| Accent-only | normal weight + ColorAccent foreground | Menu mnemonic column `[r]`, logo default color |
| Muted-only | normal weight + ColorMuted foreground | Titled border characters, title label text |

Rules (unchanged from Phase 1):

- Maximum 2 concurrent text attributes on any single piece of text (bold + color is fine; bold + italic + underline is not).
- Underline reserved for hyperlinks in help text (not used in Phase 7 chrome).
- Italic not used — poor rendering in most terminal emulators.
- No per-frame style allocation. Every style is a package-level var in `internal/ui/styles.go`. Grep-gated.

Phase 7 title typography (within titled-border top line):

- Title string renders inline inside the border top line: `╭─ Title ─...─╮`
- Title text color: inherits from ambient render (no override — border line color wins by default). If a distinct foreground is needed, `TitleLabelStyle` package var applies `ColorMuted` to the title string specifically. Final decision: title is styled with `TitleLabelStyle` (ColorMuted) to maintain the "quiet, structural" feel of the border.

### 60/30/10 interpretation for Phase 7 chrome

- **60% (Background, `#1e1e2e`):** Terminal background continues to dominate. The chrome row adds 6 rows of largely-empty space (logo ~25 cols of art, menu 2×6 grid of text rows, info-panel placeholder blank) — background still shows through the chrome gutters.
- **30% (Surface, `#313244`):** Status bar and help overlay remain the only surface-backed regions. Phase 7 chrome adds NO surface fills — the header region is transparent to the terminal background. This preserves k9s visual parity (k9s header is also background-transparent, with content floating on the default cell).
- **10% (Accent, `#89b4fa`):** Menu mnemonic labels `[key]` and the logo become new accent hotspots. The accent "10%" budget is respected because menu mnemonics occupy only ~3-5 chars per cell in a 2×6 grid (total ≤60 cells of accent ink), and the logo occupies ~6 rows × 25 cols of mostly-sparse ASCII art (not solid fill). Combined chrome accent usage is well under the 10% threshold.

## Copywriting Contract

Phase 7 introduces no new user-facing copy in error/empty/destructive paths — all such paths are owned by v1.0 sub-models and remain unchanged. Phase 7 adds **chrome text** (titles + menu hint descriptions), which is a new copy surface.

### Titled border titles (per-state, locked by D-15)

Title format rule: list views use bare parenthesized count `(N)`; Health uses unit-ful `(N findings)` deliberately (user picked the preview with this variance); contextual views use `Subject: <name>` colon-separated; static views use view name only. Every title has exactly one leading space and one trailing space inside the border overlay: `" Files (12) "`.

| State | Title literal (with spaces for overlay) | Source of count/subject |
|-------|----------------------------------------|-------------------------|
| `stateFileList` | `" Files (N) "` | `m.fileList.ItemCount()` |
| `stateDetail` | `" Detail: <filename> "` | `m.currentFile.Name` (no git badge in title — filename only) |
| `stateMetadata` | `" Metadata "` | — |
| `stateDiff` | `" Diff "` | — |
| `stateHelp` | `" Help "` | — |
| `stateHistory` | `" History (N) "` | `m.history.CommitCount()` |
| `stateHealth` | `" Health (N findings) "` | `m.health.FindingCount()` — unit-ful deliberately |
| `stateRecipientList` | `" Recipients (N) "` | `len(m.currentFile.Recipients)` |
| `stateRecipientForm` | `" RecipientForm "` | — |
| `stateFormatMenu` | `" Format "` | — (overlay — Plan 3 decides if titled border applies) |
| `stateRecipientConfirm` | `" Diff "` | Shared body with `stateDiff` |
| `stateBulkReKeyConfirm` | `" Diff "` | Shared body with `stateDiff` |

Overlong-title rule: if `Width(title) > width - 4`, truncate with `…` (U+2026 ellipsis is a box-drawing-allowlist exception — verify in `TestChromeASCIIOnly` allowlist or use `...` three-ASCII-dot fallback; Plan 2 author decides). **Recommendation: use `…` and extend the allowlist, since lipgloss `ansi.Truncate` already produces it and the character is font-universal.**

### Menu hint descriptions (derived from `key.Binding.Help().Desc` — single source of truth)

Per D-08, menu text is not hand-written — it comes from `key.Binding.WithHelp(mnemonic, description)` already defined in `internal/keys/bindings.go`. The copywriting contract therefore applies to the **existing help strings** which become visible chrome in Phase 7 for the first time.

Rules for menu description copywriting:

- Lowercase verb + noun or noun phrase — e.g., `move up`, `toggle help`, `toggle select`, `reveal/hide value`, `bulk re-key selected`, `health check`.
- No trailing period.
- No exclamation points.
- Maximum ~20 chars description — fits a 2-column menu grid without wrapping at typical terminal widths.
- Imperative mood for actions: `move up` (not "moves up"); `quit` (not "quits").
- Past participle for state toggles: `toggle select` (not "select and deselect").

Mnemonic column rules (rendered inside `[` `]` brackets):

- Single-key: `j`, `/`, `?`, `q`
- Arrow-and-letter alternate: `j/↓`, `k/↑`, `h/←`, `l/→` (arrows are box-drawing allowlist characters)
- Modifier-combined: `ctrl+u`, `ctrl+d`, `ctrl+y`, `ctrl+c`
- Named keys: `enter`, `Esc`, `space`, `tab`
- Uppercase vs lowercase per key (Shift-modified keys rendered capital): `K` (bulk re-key), `R` (reveal all), `H` (health), `X` (rotate), `G` (go to bottom), `E` (edit in $EDITOR)
- Pair forms (sister keys): `y/n` (confirm/cancel), `1-9` (numeric selection)

These rules are already honored by existing `key.WithHelp(…)` declarations in `internal/keys/bindings.go:29-291` — Phase 7 authors should NOT modify help strings; they instead extend `ShortHelp()` returns to include `g/G` etc. as needed per sub-model curation (up to 12 visible slots per D-06).

## Interaction Contract

Phase 7 changes the frame but not the interaction model. The state machine, keybindings, and navigation patterns from v1.0 remain unchanged. Phase 7 adds **visibility** of existing keybindings via the persistent menu.

### Keybindings (Phase 7 changes)

**No new keybindings in Phase 7.** All keybindings inherit from existing `internal/keys/bindings.go` (v1.0) + Phase 5 additions. The persistent menu renders these existing bindings; it does not create them.

The `?` full-screen help overlay from Phase 1 is retained (UI-11) as the complete reference. Day-to-day keys are visible in the persistent menu so `?` is no longer required for discovery.

### Navigation model (unchanged from v1.0)

Single-pane drill-down. Phase 7 does not introduce a second pane. The titled border visually delimits the active view; no focus indicators (Pitfall 7 / D-21 — no `FocusedBorder`/`UnfocusedBorder`).

### `AppModel.View()` composition (D-17)

```
┌─────────────────────────────────────────────────────────────┐
│  [Info panel placeholder 38×6]  [Menu 2×6]     [Logo 25×6]  │  ← chrome (6 rows)
├─────────────────────────────────────────────────────────────┤
│                                                              │  ← crumbs placeholder (0 rows, Phase 8 inflates)
├─╮ Files (12) ╭──────────────────────────────────────────────┤  ← titled body top border with overlay
│ │                                                            │
│ │   fileList content rendered at (w-2) × (h-2)               │
│ │                                                            │
╰─┴────────────────────────────────────────────────────────────╯  ← titled body bottom border
 sops-tui > files    │   12 items   │  sops:✓  age:✓           │  ← status bar (1 row)
```

Composition order (JoinVertical top-to-bottom):
1. Chrome (6 rows): `JoinHorizontal(lipgloss.Top, infoPanelBlank, menu, spacer, logo)` where `infoPanelBlank` is `lipgloss.NewStyle().Width(infoPanelWidth).Height(6).Render("")` — reserves Phase 8 space (Pitfall 1).
2. Crumbs placeholder (0 rows in Phase 7): `""` — Phase 8 flips to real breadcrumb chip row.
3. Titled body: `WrapTitled(title, body, w, h)` where `(w, h) = bodyDims(m)` — body itself rendered at `(w-2, h-2)`.
4. Status bar (1 row): unchanged from v1.0 (`m.status.View(m.width)`).

### First-frame safety (Pitfall 5)

Before any chrome or body rendering, `View()` must early-return if `m.width == 0 || m.height == 0`:

```go
if m.width == 0 || m.height == 0 {
    v := tea.NewView("")
    v.AltScreen = true
    return v
}
```

This prevents `RenderMenu(hints, 0)` panic potential on lipgloss/v2/table at zero width and preserves Phase 6's existing guard.

### Narrow-terminal contract (40×12, D-04)

At 40×12 terminal size, the chrome layout degrades gracefully but is not re-laid-out:
- Logo occupies ~26 of 40 columns.
- Info-panel placeholder recommended 38 cols — exceeds viewport at 40 cols. Acceptable: the placeholder is blank, excess clips to the right edge without visual artefact.
- Menu occupies residual columns (negative after logo + info-panel-placeholder). `lipgloss/v2/table` handles negative width by rendering as minimum-width cells (implementation-defined; verified via golden refresh at 40×12).
- Titled body: `bodyDims(40, 12) = (40, 12 - chromeHeight - statusBarHeight) = (40, 12 - 6 - 1) = (40, 5)` — body region is 5 rows tall, 40 cols wide, inner `(38, 3)` after border.

Phase 10 (UI-16) addresses narrow-terminal survival more fully — Phase 7 just has to avoid crashes and layout corruption, not aesthetic perfection.

### Bench budget (D-24)

`TestBenchmarkAppView_UnderBudget` asserts `View()` wall-clock ≤ 50µs/op at 200×60 with full Phase 7 chrome rendered. Enforced via the three guardrails:
1. Styles as package vars (grep-gate D-22).
2. No `lipgloss.NewStyle()` inside `View()` (AST walker D-22).
3. Pure composition (no caching; D-18).

If this budget regresses in Phase 10 after palette changes, caching may be introduced without public API change.

## Accessibility

Phase 7 accessibility posture (full redundant-encoding scope lands in Phase 10 per UI-14):

- **Color-only encoding avoided where possible:** Menu mnemonics use bracketed `[key]` syntax — the bracket shape is text content that survives grayscale rendering. Menu description text is always `ColorFg` (readable without accent). Logo is accent-only (decorative, conveys no state information in Phase 7 — UI-03 severity coupling deferred).
- **No focus ring:** Phase 7 chrome has zero focus indicators. Pitfall 7 / D-21 enforce this via grep-gate — `FocusedBorder`/`UnfocusedBorder` are banned literals.
- **Narrow-terminal survival:** 40×12 is the minimum supported size in Phase 7. Content may look cramped but must not truncate critical data (titles can truncate; menu cells can clip). Phase 10 (UI-16) fully addresses narrow-terminal rendering.
- **Terminal-emulator portability:** `NormalBorder()` is the font-universal border style per Pitfall 12 (macOS Terminal default font cannot render `RoundedBorder`'s `╭╮╰╯` reliably, but these are the ONLY non-ASCII chars Phase 7 uses — allowlisted explicitly). ASCII-only logo guarantees portability.
- **Color-profile downsampling:** Phase 7 assumes TrueColor terminal. Phase 10 (UI-13) adds 16-color fallback palette + `lipgloss.ColorProfile` detection. Phase 7 chrome at TRUE + ANSI256 + ANSI renders correctly (verified by Phase 6 teatest profile coercion); at ASCII profile the accent color collapses to a single-color fallback — menu mnemonics lose their accent highlight but bracket syntax still denotes the key. Acceptable Phase 7 posture.
- **Keyboard-only access:** unchanged — sops-tui is keyboard-only by core value. No mouse interactions.
- **Screen reader compatibility:** not evaluated (terminal app; out of typical a11y scope).

### §confirm-flow-quit-suppression

In `stateRecipientConfirm` and `stateBulkReKeyConfirm`, the persistent
keybinding menu intentionally **omits the `[q] quit` hint**. The user
must resolve the y/n decision before exiting to prevent accidental
acknowledgement of a partially-actioned destructive flow.

This is the contract that makes `keys.RecipientConfirmHints` (5 entries,
no `q`) and `keys.BulkReKeyConfirmHints` (5 entries, no `q`) different
from `DiffModel.Hints()` (6 entries, includes `[q] quit`). The diff body
is the same in all three states; the *menu* differs by state per the
dispatcher arms at `internal/app/model.go:1466-1469`.

The Phase 7 implementation at `internal/keys/hints.go` and
`internal/app/model.go` already enforced this behaviour; Phase 7.1
(per 07.1-CONTEXT.md D-123, D-124) makes the intentionality explicit
through doc comments on both hint-set declarations and both dispatcher
arms, plus this §confirm-flow-quit-suppression subsection as the
single source of truth.
